# fft (streaming FFT accelerator)

## What it is

A synthesizable, parameterizable streaming **Fast Fourier Transform** accelerator.
It accepts one complex sample per clock and, after the pipeline fills, produces
one complex frequency bin per clock.

## Architecture

Radix-2 decimation-in-frequency (DIF) **single-path delay feedback (R2SDF)**:

- `LOG2N = log2(N)` pipeline stages (`fft_bf2sdf`).
- Each stage = a radix-2 butterfly + a **feedback delay line** of depth
  `N/2^(stage+1)` + a **complex twiddle multiplier** fed by a shared sine ROM.
- One complex sample in / out per clock; total latency `~N + LOG2N` cycles.

### Parameters

| Parameter | Default | Meaning                                   |
|-----------|---------|-------------------------------------------|
| `N`       | 64      | FFT size; power of two, `2 <= N <= 256`   |
| `DW`      | 16      | Data width, Q1.15 signed fixed-point      |

`N <= 256` because the twiddle source is a 256-entry sine ROM (see below).

### Scaling

Each stage scales its butterfly outputs by 1/2, so the result is the true FFT
**divided by N** (block scaling that keeps Q1.15 from overflowing).

### Output order

Native R2SDF order, i.e. **bit-reversed** frequency bins. A consumer that needs
natural order must reorder (e.g. a bit-reversal buffer), which is intentionally
left out to keep the core small.

## Twiddle ROM: why it maps to LUTs, not BRAM

The sine table is a synthesizable 256-entry `case` (`sinrom`) read
**combinationally** by each stage. It is deliberately **not** a BRAM, and that
is the correct mapping here:

- FPGA block RAM (Xilinx RAMB18/36, zeroasic `sdpram`, etc.) has a
  **synchronous read** only. A combinational ROM therefore cannot map to BRAM
  on any fabric -- it becomes LUTs. Verified: on both `zeroasic_z1015` and
  `xilinx_virtex7` the design synthesizes with **zero BRAM**; the table folds
  into LUTs.
- On `zeroasic_z1015` it could never be BRAM regardless: that fabric's BRAM is
  `init none` (no contents preload), so a constant ROM has no way in. (The
  synthesis flow also runs `--ignore-initial`, which strips `initial`-block
  memory loads -- this is what broke the previous version's `sine_lut`. The
  `case` ROM survives because it is logic, not an initialized array.)
- At 256 x 16 = 4 Kbit the LUT ROM is small and keeps the twiddle path
  single-cycle. Forcing it into BRAM would require a **registered (synchronous)
  read**, adding a pipeline cycle to the twiddle path (and re-aligning the
  butterflies / output latency), and would waste a whole BRAM per stage -- not
  worth it for a table this size.

So the twiddle multiplies map to DSP blocks and the ROM/control map to LUTs,
which is the intended shape of this accelerator.

## Files

- `rtl/fft.v` -- the accelerator (top `fft` + `fft_bf2sdf` stage + `sinrom`).
  Generated by `genfft.py` (the generator emits the exact twiddle `case`).
- `genfft.py` -- regenerates `rtl/fft.v` (e.g. to change the ROM resolution).
- `testbench/test_fft_smoke.v` -- Verilog-2005 self-checking smoke test:
  streams impulse / DC / tone / pseudo-random frames and compares the DUT
  output against a behavioral DFT reference (computed with `$sin`/`$cos`),
  accounting for the 1/N scaling and bit-reversed order, and searching for the
  pipeline-latency offset. Run, e.g.:

  ```
  iverilog -g2005 -o sim.out rtl/fft.v testbench/test_fft_smoke.v
  vvp sim.out
  ```

  (Add `-DWAVES` for a VCD dump.)
